# 方法对比

帮助读者决定“在我的任务和条件下，先试哪一种方法”。遵循共享成果规范与当前 methods/comparison JSON 协议。

先核对各方法的目标、输入、核心机制、资源条件、指标和适用边界。每个节点对应实际阅读的方法；用户以论文为单位比较时介绍论文本身，不用其参考文献替换节点。相同名称但不同配置分别限定条件。

name只用方法简称；summary一句定位，最多40字；detail最多两句、100字。conditions、metrics、limitations各选一个最影响采用的事实，单元格最多70字。不要将研究卡所有细节搬进正文；三种方法的常规对比应接近一页阅读量。

summary 只给简短的条件式选型判断，不放表格或节点清单。nodes 中 conditions 写任务和使用前提，metrics 保留基准、指标定义、单位和比较条件，limitations 写影响采用的局限。summary/detail 分别解释定位和机制，避免重复表格。每个事实字段就近引用直接支持该字段的短句，通常一两条足够，不按固定数量凑引用。evidence 必须等于正文实际使用的编号集合，不得复制研究卡的证据池。名称不挂引用。

跨任务数字不可直接排名；只有一项时生成方法档案；没有可比指标时按机制和前提比较，不编造共同评分。没有资源信息时把选型写成条件句，不要求用户填写与当前判断无关的参数。

仅交付一份对比成果，版式由程序生成。不输出“待核对”段落或缺口清单，gaps=[]。可选字段缺依据用null；补读后仍不能支持的判断删掉，不把缺证据写成论文有缺陷。opportunities 通常为空，除非用户同时要求验证思路。不要另写综述、技术演进或交互地图。

完成标准：比较维度一致，例外没有被压进表格后丢掉，每项建议说明适用条件。
